Machinist Job Card

One local Task, an exact Spec to approve, and a verified candidate with independent advisory Review. You choose local integration and optional publication.

AgentMachinist 0.16.0 adds clearer next-step guidance after issue creation, Spec generation, Approval requests, and Review. Install from PyPI. The separate GitHub issue workflow remains supported.

Task T1→baseline + Spec commit→approve exact SHA→Execute + gates→advisory Review→you integrate
PREP

A committed repository, a Harness, and real tests

Start with a clean Git checkout, an initial commit, configured author, and an installed, authenticated Harness. No origin, forge account, or watcher is required for local Tasks.

# Install the released controller:
uv tool install agentmachinist
machinist start --help
# Then change to the repository you want to work on:
cd ~/code/your-project
# Optional: exercise the production path in a disposable repository.
machinist rehearse

The default rehearsal uses a fake Harness with real Git and verification, making no model or API calls. rehearse --harness uses configured Harnesses and may consume provider usage.

Foreground local workflow

Recommended for solo developers and small teams. Task IDs such as T1.

Legacy GitHub issues

Existing GitHub Actions or local watcher dispatch. Numeric issue IDs such as 7.

01

Start and prepare

Local
machinist start "Add CSV export for filtered transaction rows" --test-cmd "uv run pytest"
# Optional detail from outside the checkout: --body-file ../task.md
# Read stdin: --body-file -

Save optional Task body files outside the checkout or commit them first. First start reuses configured Harness profiles or discovers an installed full-pipeline Harness, saves .machinist/runs/local/config.yaml, and runs baseline verification before model work. Select the Harness explicitly with --harness codex or another adapter.

The Gate must work from committed files in an isolated Workshop. Ignored dependencies are not copied; use environment preparation such as npm ci && npm test when needed. Local setup requires at least one required Gate and always enables Review.

GitHub setup
machinist onboard --setup-pr --spec-source github-actions

This commits and pushes managed setup changes and opens or reuses the draft PR. Add the selected adapter’s repository secret, then review and merge the setup PR before running:

machinist doctor --run-gates

Onboarding performs setup preflight before requiring remote default-branch deployment. Rerun it to resume managed setup work and reuse the draft PR. Existing valid settings are preserved; use machinist config set to change them.

For local watcher Spec dispatch, choose --spec-source local. That legacy setting still requires GitHub; it is separate from local Tasks.

02

Read the Spec

Machine Phase
Local
machinist status T1

start generates a Spec, retains its exact commit on agent/task-1, and stops for Approval. Inspect the printed Spec and full SHA. Your original base is unchanged.

Task records live under .machinist/runs/local/ and are excluded using Git’s local exclude file. Existing machinist.yaml is preserved; local setup generates no GitHub artifacts.

GitHub issue
machinist task new --title "Add CSV export for filtered transaction rows" --dispatch

Answer five terminal prompts for Objective, Acceptance criteria, Constraints, Verification, and optional Context, or add --body-file ../task.md. Use the returned issue number in later commands; 7 is illustrative. Only for github.spec_source: local, run machinist spec 7 or let the watcher dispatch it. GitHub Actions Spec dispatch runs after the trigger label is applied. It opens a draft PR containing .machinist/specs/issue-7-spec.md. A local watcher leaves that Spec Phase to CI.

The issue form accepts ## and GitHub’s ### field headings. Its Objective needs at least six words; acceptance checkboxes must be meaningful. Failed lint or publication preserves a draft.

03

Approve the exact Spec

Human Gate
Local Approval
machinist approve --task T1 --spec-sha <full-spec-commit-sha>

Copy the complete command printed by start or status after reading the Spec. Approval records repository, Task, exact SHA, actor, and time. The command continues Execute, verification, and independent Review in the foreground.

GitHub Approval
machinist approve --issue 7
# Or: machinist approve --pr 8

Alternatively, post /machinist-execute <full-spec-commit-sha> from the PR body as a PR comment. The managed workflow checks write or admin access and the current head before recording the trusted SHA marker. The CLI requests Approval asynchronously; it does not mint that Evidence. The GitHub review Approve button is not this Gate.

Wait for the approval workflow to succeed. Confirm the configured approval label is on the draft PR. Then use machinist inspect 7 --json and confirm approval_sha equals head_sha in the github_pr source before running Execute. An early run can fail and require explicit retry.

04

Execute, verify, and independently Review

Machine Phases
Continues in foreground
# Read progress in the current terminal.
# If eligible work remains after an interruption:
machinist continue T1
machinist status T1

The Harness implements in an isolated Workshop. The controller runs required Verification Gates and retains the candidate before cleanup. A separate read-only Review checks the exact candidate and saves advisory findings.

continue never bypasses Approval or explicit retry. A completed Review with findings is not a failed gate and does not certify the change safe to integrate.

Local runner or watcher
machinist run 7

Only when legacy review.enabled: true is configured, run independent Review after Execute succeeds:

machinist review 7

Execute verifies and pushes with a lease. With review.enabled: true, the PR stays draft until an independent Review completes at the exact delivered head. With Review disabled, Execute can mark it ready after verification.

Findings remain advisory. A changed successful Execute candidate can receive a fresh Review; the completed report for an earlier head is not reused.

05

Inspect and accept the result

Human decision
Explicit local integration
machinist status T1

Status prints the candidate SHA and Review report path. Open that report and inspect git diff <spec-sha> <candidate-sha> using the exact SHAs from status before integrating:

machinist integrate T1

Integration requires a clean checkout of the expected base, exact base and reviewed candidate commits, and fast-forward ancestry. Intent is saved before the update so retry can reconcile an interruption. Nothing is pushed.

Human remote merge

Inspect the PR diff, Verification Evidence, and any Review findings. Merge the remote PR yourself. AgentMachinist does not perform remote or automatic merges.

Legacy amendment uses machinist amend 7 --feedback "…" after fresh Approval of the current head. Local amendment follows the new-Spec flow below.

OPTIONAL

Bring GitHub or GitLab into the local workflow

Authenticate gh or glab for the selected host. Issue intake saves provenance; imported issue 42 can become T1. Publication requires one origin matching the chosen forge and repository.

# Choose an issue source, if useful:
machinist start --from-issue https://github.com/team/project/issues/42
# machinist start --from-issue https://gitlab.com/team/subgroup/project/-/issues/42

Use the returned Task ID and complete Approval, Execute, verification, and Review before publishing. Choose one provider matching origin, before or after local integration:

machinist publish T1 --provider github
# Or:
# machinist publish T1 --provider gitlab
# Explicit self-managed GitLab host:
# machinist publish T1 --provider gitlab --host gitlab.example.com

Publication verifies exact local Approval, successful Execute and Review, candidate identity, and its recorded remote lease. Retry the same command after a failure to reconcile the push or PR/MR without repeating successful Harness work or gates. GitLab supports issue import and MR publication, including nested projects and explicit hosts; hosted Spec CI and remote GitLab Approval are not included.

Amend and recover local Tasks

After completed verification and Review, before integration, create a fresh Spec from feedback. Read it before approving its new SHA:

machinist amend --task T1 --feedback "Also test empty filtered results."

For a failed Phase, choose one recovery command. Execute defaults to resuming retained edits:

machinist retry --task T1 --phase execute
# Or use a fresh Workshop:
# machinist retry --task T1 --phase execute --fresh
# For another failed Phase instead:
# machinist retry --task T1 --phase spec
# machinist retry --task T1 --phase review

To request cooperative cancellation:

machinist cancel --task T1 --reason "Requirements changed"

Resolve the cause before clearing cancellation with machinist cancel --task T1 --clear, then follow the recovery action from status.

Amendment requires a verified candidate with completed Review. It invalidates earlier Approval and requires Review of the new candidate. To reject an initial Spec before Approval, cancel that Task and start a new one with clearer context. Once integration has begun, start a new Task from the current base. Resolve a pending publication before replacing its candidate. Legacy numeric Execute retry remains machinist retry 7 --phase execute --run --resume; its default is fresh.

Exact human decisionsApproval authorizes one Spec commit. Integration and publication are separate explicit operations.
Controller owns GitThe Harness must not commit, push, or edit protected Task metadata. Custody checks reduce credentials and detect violations, without OS isolation.
Local is not offline inferenceThe Harness may use a cloud model. Offline inference needs a local provider, cached models and dependencies, and separate network-denied validation.
One runner checkoutSmall teams can share issues and PRs/MRs while one operator owns local Tasks. Claims do not coordinate separate checkouts. Watcher Task Run budgets do not limit foreground local Tasks.

Available since 0.15.0: optional machinist doctor --local checks readiness without forge setup or local Task state. Add --run-gates only to execute project commands in the controller checkout; isolated Workshop baseline verification still runs at start.

New in 0.16.0: completion messages suggest the next activity and command after issue creation, Spec generation, Approval requests, and Review.
